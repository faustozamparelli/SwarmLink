# Working preferences

- Keep changes lean, modular and limited to the requested scope. Avoid speculative infrastructure, extra dependencies, duplicated functionality and elaborate patterns.
- Complete authorized work and routine verification without repeated permission questions. Ask only about consequential unresolved choices; distinguish proposals from established requirements.
- Preserve source-of-truth documents unless changes are explicitly authorized. Update living implementation documentation after meaningful changes with actual behavior, decisions, test results, limitations and useful study pointers. Keep a concise change log.
- Document reproducible commands and generated outputs in README. Report failures and limitations honestly; never present planned work as implemented or omit failed cases from evaluation.
- Write focused tests for important behavior and failure cases. Run the relevant checks and inspect generated plots or other visual artifacts.
- Use Context7 for current library/framework/SDK/API/CLI/cloud documentation: resolve the library ID first, then query the relevant docs. Prefer official documentation as fallback if unavailable. General programming and business-logic work do not require a lookup.
